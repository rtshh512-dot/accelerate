# COIN-BIEVR CUDA 加速方向报告

日期：2026-11-13。对象：当前两阶段配准、自适应 λ、弱方向选点及 v32–v36 加速分支。本文是设计方案，尚未实现或测得 CUDA 加速比。

## 1. 目标与现状

目标是在尽量保持现有轨迹精度的条件下，降低单帧端到端耗时，重点处理反复迭代的配准阶段。现有 RunwayD 分阶段记录中，配准约 17.03 ms、地图更新约 6.14 ms、采样约 2.49 ms、整帧约 32.10 ms；这些是先前 CPU 运行的单次口径，不能直接作为 CUDA 版本的预期结果。v32 几何探测已通过减少整段几何迭代实现部分加速，CUDA 应与其做增量比较。

当前 `LsqRegistration::linearize` 对每个采样点做：位姿变换 → 体素查找 → 局部图插值及梯度 → 几何/强度残差和 6 维雅可比 → 鲁棒加权 → 累加 6×6 信息矩阵 H、6 维向量 b、误差和有效点数。该过程在 LM 的每次线性化及试探位姿评价时重复，现由 TBB 在 CPU 上并行。矩阵求解规模很小，搬到 GPU 的潜在收益有限。

## 2. 首要硬件条件

用户目前的 VMware 客户机只显示 `VMware SVGA II Adapter`，且 `nvidia-smi` 不存在。这说明当前 VM 没有可见的 NVIDIA 计算设备。**安装 CUDA 或 NVIDIA 工具包本身不能让该 VM 运行 CUDA 核函数。** 实验需要可访问 NVIDIA GPU 的 Linux 主机、云端实例，或经验证可用的 GPU 直通环境。首先在目标运行环境检查 `nvidia-smi`、CUDA 驱动兼容性和简单核函数；未满足前，不应投入完整 CUDA 移植。

## 3. 推荐改造方案

### 3.1 保持算法，先迁移逐点线性化

第一版保留两阶段顺序、λ 和弱方向计算规则、LM 接受/拒绝规则及 CPU 的 6×6 求解器。GPU 负责批量逐点变换、体素关联、图像采样、残差与雅可比计算，并分块归约得到 H、b、损失及有效点数。CPU 只接收归约后的少量数据并计算位姿增量。LM 的试探损失也在 GPU 上计算，避免每次试探下载逐点残差。

对单点残差 rᵢ、雅可比 Jᵢ 和鲁棒权 wᵢ，GPU 累加的是 H=ΣwᵢJᵢᵀJᵢ、b=ΣwᵢJᵢᵀrᵢ；几何、强度及附加残差的分块统计须与 CPU 版对应。λ 已进入强度残差及雅可比时，必须维持相同的缩放顺序，避免重复乘 λ 或改变 H 中 λ² 的作用。

### 3.2 为 GPU 建立只读局部地图快照

现有地图以 CPU 对象、哈希查询和 `const Voxel*` 缓存工作。GPU 版本需要连续布局的点数组、体素键与索引、体素变换、平面/高度图及强度图数据；查询结果用整数体素索引，不保存 CPU 指针。每帧在地图更新完成后生成或更新局部地图快照，整个配准期间固定该快照。将直接命中及邻域搜索的规则逐项移植，尤其要保留“本格无有效体素时才寻找邻格、按中心距离决定关联”的语义。v32 的指针复用不能原样移植到 GPU。

地图快照应只覆盖可能被当前点云访问的局部区域，并记录快照版本。若局部地图过大或每帧重建/传输太慢，再考虑增量维护 GPU 体素表。不要一开始重写完整地图更新系统。

### 3.3 尽量减少传输和分配

扫描点与强度、预计算的点斜对称矩阵可按帧上传；当前位姿每次迭代只传少量参数。保留 GPU 缓冲区，避免每帧重复申请显存。每次线性化仅回传 H、b、误差、匹配数和必要诊断计数。地图更新仍在 CPU，更新后再同步受影响的局部体素。配准期间 GPU 必须读取同一个地图版本，否则两阶段的关联和 λ 诊断会失去可比性。

## 4. 实施次序

1. **硬件验证与计时基线。** 在真实 CUDA 环境运行当前 CPU 版，记录端到端、几何阶段、联合阶段、`linearize`、地图查询、上传下载及迭代次数的均值和 P95。CPU 基线须与 CUDA 版在同一机器上测量。
2. **只做几何线性化原型。** GPU 生成几何 H、b、损失；CPU 维持优化器。逐帧对照有效关联数、H、b、单步增量、最终轨迹。如果关联不同，先查体素哈希、边界和邻域回退。
3. **加入联合阶段。** 加入强度图插值、梯度、λ、弱方向点权及鲁棒核。分别对照几何 H、强度 H、损失、选点数，而非只看 ATE。
4. **加入 LM 试探评价。** 让被拒绝的候选位姿也在 GPU 上评价，测量迭代内的传输次数和同步开销。
5. **优化地图同步。** 在正确性稳定后才实现增量体素上传、GPU 常驻局部地图及异步传输。
6. **与 v32 组合。** 在相同 CUDA 实现上比较“完整两阶段”和“v32 探测跳过”；确认两项收益是否叠加、是否改变回退频率。

每一步保留 CPU 路径和开关，产生独立版本、配置及实验记录，便于消融和回退。

## 5. 关键风险与判断标准

| 风险 | 为什么重要 | 验证方式 |
|---|---|---|
| 体素随机访问 | GPU 线程访问不同体素，缓存命中可能低 | 单列查询核耗时及访问命中统计 |
| 地图传输 | 每帧复制大量局部体素可能抵消计算收益 | 分开记录快照构建、H2D、核函数、D2H |
| 小工作量 | v32 已省去部分几何迭代，剩余 GPU 工作可能不足 | 对比原始两阶段与 v32 两种模式 |
| 关联/数值变化 | GPU 浮点归约次序与 CPU 不同；边界点关联可能改变 | 逐帧比较关联数、H、b、位姿增量与轨迹 |
| LM 同步 | 每次试探都要等待损失结果，难以完全隐藏延迟 | 记录每轮核函数与 CPU/GPU 同步时间 |

成功标准先定为：同机端到端平均耗时和 P95 均有可重复的改善，ATE/RPE 与 CPU 基线保持在用户可接受范围内，且轨迹无新增失败段。建议至少三个场景、每个模式重复三次。若仅核函数变快而端到端不变，则不应宣称系统加速；应根据分项耗时决定是继续优化地图布局，还是停止 CUDA 路线。

## 6. 预计需要改动的模块

- `BIEVR/src/ls_optimizer.cpp`：逐点线性化、试探损失与归约的 CPU/GPU 双路径。
- `BIEVR/src/bievr_map.cpp` 及体素定义：局部地图快照的导出和版本管理；先不改 CPU 地图更新算法。
- 新增 CUDA 核函数及设备侧数据布局：体素索引查询、插值、残差/雅可比、分块归约。
- 构建与配置：可选 CUDA 构建、运行时 CPU/GPU 开关、无 GPU 时清晰报错或 CPU 回退。
- 计时与日志：几何/联合两阶段分别记录地图构建、传输、查询、计算、归约和同步。

## 7. 结论

最可信的 CUDA 切入点是**配准迭代中的逐点线性化和损失评价**，而不是 6×6 求解。主要难点是把当前依赖 CPU 指针与随机体素查询的地图，改成设备端可高效读取且关联结果一致的局部快照。当前 VM 无可见 NVIDIA GPU，应先落实运行环境，再用几何阶段最小原型验证端到端收益，随后扩到强度与联合优化。
